# ADR-0006: Framework do painel administrativo

- **Status:** Proposto
- **Data:** 2026-11-11
- **Decisores:** pessoa (D6, respondida na seção 16/Q4 do plano aceito em 11/11/2026)
- **Requisitos:** QUA-01

## Contexto

> Este ADR não abre uma decisão nova. A decisão humana **D6** (framework do painel) já foi respondida pela pessoa na seção 16, pergunta Q4, do plano revisado aceito em 11/11/2026: **"a D6 se mantém"**, ou seja, o painel continua com **Refine Core**. Este documento registra a evidência e a comparação sem código entre as três alternativas levantadas, como pede a própria tarefa F0-03 — ele serve de **registro**, não de decisão aberta.

Fatos levantados na Fase 0 (ADR-0001, V20; plano revisado §16/Q4 e §5/O15):

- O `PLANO-EXECUCAO.md` v1.0 citava o preset `vite-shadcn` do Refine v5, mas a documentação atual mostra que esse preset traz um provedor REST sem Supabase, Vite 6, shadcn CLI 2 e React 19.1.0 — incompatível com o restante do stack combinado nesta fase.
- O **Refine Core** está em modo de manutenção: o último pacote npm é de 02/04/2026, as versões 5.1 e 5.2 não foram publicadas porque o pipeline de release está quebrado, e o foco da equipe mudou para o produto de IA deles (jan/2026) (refine.dev/blog/refine-core-introduction; github.com/refinedev/refine).
- O método `custom()` (chamadas RPC) **não é implementado** no provedor de dados Supabase do Refine — relevante porque o painel precisa chamar RPCs do schema `curation`.
- `apps/painel` só nasce na Fase 3; o único efeito desta decisão sobre a Fase 0 é o formato do `theme.css` ser neutro (formato shadcn atual, com `oklch`) — não há código do painel nesta fase.

## Decisão

**Mantém-se o Refine Core**, conforme decisão humana D6 (já tomada, seção 16/Q4). Nenhuma mudança de framework é proposta. A tabela abaixo é a comparação sem código feita nesta fase entre as três alternativas levantadas, para registro e para apoiar qualquer revisão futura da D6:

| Critério                        | Refine Core (pinado) — **escolhido**                                                                                                                                                               | shadcn-admin-kit + ra-supabase-core                                                                                                                 | TanStack Router/Table + shadcn                                                                                                                                                                                       |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lista                           | `useTable`/`useList` com paginação, ordenação e filtro embutidos; hooks maduros e documentados para CRUD sobre Supabase                                                                            | React Admin (via shadcn-admin-kit) com `<List>`/`<Datagrid>`; maduro, mas acopla a convenções do React Admin                                        | Sem camada de dados pronta: `@tanstack/react-table` só renderiza; busca/paginação/filtro são escritos à mão sobre `supabase-js`                                                                                      |
| Filtro                          | `useTable({ filters })` integrado ao provedor de dados; filtros compostos suportados                                                                                                               | `ra-supabase-core` traduz filtros do React Admin para `.filter()`/`.or()` do PostgREST; funciona, mas depende de convenções do React Admin          | Nenhum filtro pronto; implementação manual com `supabase-js`, mais controle, mais código próprio para manter                                                                                                         |
| Paginação                       | Embutida no provedor de dados Supabase (`range`/`count`)                                                                                                                                           | Embutida via `ra-supabase-core`, segue o padrão do React Admin                                                                                      | `@tanstack/react-table` tem paginação client-side; paginação server-side exige código próprio sobre `supabase-js`                                                                                                    |
| Login                           | `@refinedev/supabase`'s `authProvider` cobre login, logout e `checkAuth` prontos                                                                                                                   | `ra-supabase-core` tem `authProvider` próprio para Supabase Auth, equivalente em maturidade                                                         | Nenhum pronto; TanStack Router dá roteamento e guards, mas a integração com Supabase Auth é escrita à mão                                                                                                            |
| `app_role` (controle de acesso) | Hooks de `can`/`accessControlProvider` do Refine permitem checar `app_role` por recurso/ação, mas exigem mapeamento manual das regras                                                              | React Admin tem `authProvider.canAccess`, com modelo equivalente de mapeamento manual                                                               | Sem convenção: controle de acesso por `app_role` seria 100% código próprio, com ou sem RLS como última linha de defesa                                                                                               |
| RPC no schema `curation`        | **Lacuna conhecida**: `custom()` não é implementado no provedor de dados Supabase do Refine — chamadas RPC exigem contornar o provedor (chamada direta a `supabase-js` fora do padrão `useCustom`) | Sem gap documentado de forma equivalente nesta fase: `ra-supabase-core` não foi auditado quanto a RPC; tratado como desconhecido, não como vantagem | RPC via `supabase-js` direto, sem camada intermediária — "funciona" porque não há abstração para contornar, mas também não há padrão de cache/estado (nenhuma camada de query, a não ser que se some TanStack Query) |
| Manutenção do projeto upstream  | Em modo de manutenção (sem release de minor desde abr/2026, pipeline quebrado, foco da equipe mudou) — risco para o longo prazo, mitigado por pin de versão                                        | Composição de dois projetos (shadcn-admin-kit sobre React Admin); risco de manutenção distribuído entre dois upstreams                              | Sem dependência de framework de admin; risco de manutenção concentrado no próprio time (mais código próprio para manter)                                                                                             |

## Consequências

- A Fase 0 não implementa nada do painel; o único efeito prático é o formato do `theme.css` já nascer neutro (compatível com o tema atual do shadcn), como já decidido no O15.
- A lacuna de `custom()`/RPC do Refine com Supabase (relevante para o schema `curation`) é um risco conhecido e aceito ao manter Refine Core; a Fase 3 (quando `apps/painel` nasce) precisa de um padrão explícito para chamadas RPC que contorne essa lacuna (ex.: hook próprio sobre `supabase-js`, fora do data provider).
- O estado de manutenção do Refine Core (sem release de minor desde abril/2026) é um risco de longo prazo registrado aqui; se a situação piorar (ex.: falhas de segurança sem correção), a D6 pode ser reaberta citando este ADR como linha de base de comparação.
- Este ADR não precisa ser revisto para a Fase 0 seguir; só precisa ser revisto se a D6 for reaberta no futuro (por exemplo, na Fase 3, quando o painel é efetivamente construído e a lacuna de RPC se tornar bloqueio real).

## Alternativas consideradas

- **shadcn-admin-kit + ra-supabase-core**: rejeitada para a Fase 3 por ora — não resolve o gap de RPC de forma comprovadamente melhor (não auditado nesta fase) e soma dois upstreams (shadcn-admin-kit sobre React Admin) em vez de um.
- **TanStack Router/Table + shadcn**: rejeitada para a Fase 3 por ora — zero camada de dados pronta significa reescrever lista, filtro, paginação, login e controle de acesso à mão; mais controle, mas mais código para manter, sem ganho claro sobre o gap de RPC que motivaria a troca.
- **Refine Core (mantido)**: aceito pela decisão humana D6 (seção 16/Q4) apesar do modo de manutenção do projeto upstream e da lacuna de RPC, porque nenhuma alternativa comparada resolve o gap de RPC de forma comprovadamente melhor nesta fase, e a troca de framework não é tarefa de código na Fase 0.
